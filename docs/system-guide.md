# Butler 系统说明书（人话版）

> 这份文档写给「人」看，不是给机器看。
> `docs/contracts.md` 是技术契约（字段、接口、状态机），本文件回答三个问题：
> **它现在能干什么？它内部怎么转？它和最初设想差多少？**

---

## 一、一句话概括

一个跑在飞书上的个人时间管理助手：你随口说一句话，它理解你的意思、把该记的记进数据库，到点主动来提醒你。

它不靠「记住你说过什么」来工作，而是靠**记录**来工作——说过的每句话、做过的每个动作都写进数据库，需要时去查。这是刻意的设计，不是缺陷（原因见第四节末尾）。

## 三、系统是怎么运转的

### 3.1 六个部件（用比喻理解）

| 部件 | 代码位置 | 比喻 | 干什么 |
|---|---|---|---|
| 渠道适配器 | `app/adapters/` | **前台接待** | 把飞书的消息翻译成系统能懂的样子，再把系统的回复翻译回飞书。只有这里碰飞书 SDK，换渠道不影响其他部分 |
| 入站管道 | `app/engine/pipeline.py` | **办事窗口** | 查白名单、去重、落库，3 秒内必须办完（飞书有超时要求），然后把活转给后台 |
| Friday | `app/agents/friday/` | **快通道大脑** | 理解你的意图，决定调哪个工具，最多 4 步；带最近对话历史 |
| Worker + 触发器 | `app/worker/`、`app/engine/triggers.py` | **闹钟管家** | 每秒看一眼有没有到点的 trigger，到点就处理；失败退避重试 |
| 物化器 | `app/engine/materializer.py` | **排班员** | 每 5 分钟补排未来 3 天的简报；块的提醒在排块/改期时立即排好；设置改了会重排 |
| 仲裁器 | `app/engine/arbiter.py`（纯判断）+ `app/engine/nudge.py`（执行） | **门卫** | 所有主动消息的唯一出口：发 / 延后 / 并入简报 / 丢弃，每个决定写决策日志 |
| LLM 网关 | `app/llm/` | **模型总机** | 所有模型调用都从这里走，统一记录、统一限额。档位别名在 `app/llm/aliases.yaml` |

### 3.2 一条消息的旅程

```
你在飞书发「周三下午3点提醒我交报告」
  ↓
① 飞书长连接收到 → 前台接待翻译
  ↓
② 办事窗口：查白名单 → 找到你的档案 → 去重 → 写进日记本（event_log）
   （以上 3 秒内完成，立刻给你一个「收到了」的内部信号）
  ↓
③ 快通道大脑登场：带着「当前时间 + 你的时区 + 最近对话 + 13 个工具」去问模型
  ↓
④ 模型说「我要调用 set_reminder，时间是 2026-11-11T15:00:00+08:00」
  ↓
⑤ 工具真的写进数据库（提醒表 trigger_instance，状态 pending）
  ↓
⑥ 模型再回答你一句「已帮你设好」
  ↓
⑦ 前台接待把这句话发回飞书
  ↓
⑧ 另开一笔账：记下「我回了什么、发成功了没有」
```

### 3.3 一个提醒的旅程

```
排班员每 5 分钟补排：未来 3 天的简报 + 每个块的「开始前 10 分钟」提醒
（你改简报时间、改块时间，旧的排班作废并重排）
  ↓
闹钟管家每秒轮询一次数据库
  ↓
发现有 trigger 到期 → 领取（打上「我在处理」标记，防止重复发）
  ↓
检查：已经过期太久？→ 标记 missed（停机错过）
      前提变了（任务已放弃 / 块已完成或改期）？→ 标记 dropped（不打扰你）
  ↓
生成候选（提醒 / 块开始 / 简报；逾期检查只记信号，不发消息）
  ↓
门卫仲裁：
  ├─ 正在免打扰（默认 23:00–07:00）→ 延后到免打扰结束；延了 3 次还不行就丢弃
  ├─ 简报这种「每天 1 条」的类型今天已发过 → 丢弃
  ├─ 建议并入数超过每日预算（默认 4 条）→ 丢弃
  ├─ 建议类 → 并入下一次简报，不单独发
  └─ 放行 → 发送到你飞书
  ↓
发送成功 → 标记 fired，同时写投递记录和决策日志
发送失败 → 这次的决策与错误先落库（独立提交，不会被回滚），
           再 30 秒后重试，失败 60 秒、120 秒…最多 5 次
           5 次都失败 → 标记 failed，并记录原因供事后查
```

简报本身的内容全部由代码按数据库查询拼出来（今天几个块、哪些没完成、昨天统计），
模型只负责写开头那一句话（比如「早上好」），写失败就用固定文案，不会编造清单。

### 3.4 三条数据线

| 数据 | 表 | 比喻 | 特点 |
|---|---|---|---|
| 对话与事件 | `event_log` | **日记本** | 只增不改，说过什么永远可查 |
| 业务状态 | `work_item`（任务）、`planned_block`（计划）、`trigger_instance`（提醒）、`user`（用户） | **台账** | 有严格结构，随时可精确查询 |
| 模型账本 | `llm_call` | **账本** | 每次调用的输入、输出、token 消耗、耗时、错误 |

派生数据（摘要、向量、抽取的事实）设计上都带「来源是哪几条事件」的引用，随时可以重建——这是为了「日记本永远是真相，其他都是可再生的总结」。

## 四、和最初设想的对照

**你的设想：两个助手分工——Friday 管日常高频小事，Jarvis 管长期复杂大事。**

| | Friday（快通道） | Jarvis（慢通道） |
|---|---|---|
| 设计定位 | 日常高频、低难度、小颗粒度 | 长期任务立项、重规划、周复盘 |
| 代码实现 | ✅ 完整 | ❌ **零行代码** |
| 运行方式 | 收到消息立即处理（同步，秒级） | 设计为异步排队 + 显式状态机 |
| 用的模型 | `friday_fast`（Coding 套餐，天天在用） | `jarvis_deep`（Agent 套餐的 kimi，配好但从未调用） |
| 数据地基 | 普通任务、提醒 | 使命/项目类型、计划表的「jarvis 安排」枚举已预留 |

**结论：分工在设计上明确，在代码里只落地了一半——快通道完成了，慢通道只有名字。**

Jarvis 这三个字目前只出现在：模型档位配置、计划表的「谁安排的」枚举、任务表的「长期任务」类型。没有任何智能逻辑。

现实后果：
- 你说「我想开始一项长期任务」，实际是 Friday 在回你——它只能反问三件事，然后建一个普通任务，**不会立项、不会拆解、不会规划**
- 系统现在会主动发出的有三类：到点提醒、块开始前提醒、每天早晚两条简报。它们都由确定性规则触发，模型只在简报开场语上出现一次

**为什么先做成这样？** 项目当前是 P0 阶段，目标是验证机制（消息如何进来、状态如何写、失败如何重试），不是堆功能。Jarvis 的地基（任务层级、计划表、异步队列、模型档位）都已经铺好，后续阶段可以直接在上面长。

**关于「它记不住上下文」**：这是有意的边界。设计原则是「模型只通过工具读写状态，不依赖回忆」——该记住的事应该写进任务表或记忆表，需要时让模型去查，而不是靠对话历史里的一次性记忆。短期连贯性已经补上（每条消息带最近 12 条对话）。跨天事实现在能写入数据库（带来源与决策记录），但还不会在对话或简报里被主动调用——读取与画像注入是阶段 3b。

## 五、你可以调的开关（`.env` 文件）

| 变量 | 作用 | 当前值 |
|---|---|---|
| `FEISHU_APP_ID` / `FEISHU_APP_SECRET` | 飞书机器人身份 | 已配 |
| `LLM_BASE_URL` / `LLM_API_KEY` | Friday 用的 Coding 套餐端点 | 已配 |
| `LLM_AGENT_BASE_URL` / `LLM_AGENT_API_KEY` | Jarvis 用的 Agent 套餐端点 | 已配 |
| `ALLOWED_OPEN_IDS` | 谁能用这个机器人（逗号分隔） | 空 = 不限制 |
| `LLM_DAILY_LIMIT` | 每人每天模型调用上限 | 200 |
| `DEFAULT_TIMEZONE` | 新用户默认时区 | Asia/Shanghai |
| `WORKER_POLL_INTERVAL` | 闹钟管家轮询间隔（秒） | 1 |
| `TRIGGER_LEASE_SECONDS` | 提醒处理超时回收时间（秒） | 300 |
| `BLOCK_LEAD_MINUTES` | 块开始前多少分钟提醒 | 10 |
| `BLOCK_GRACE_MINUTES` | 块结束后多少分钟检查是否完成 | 15 |
| `REMINDER_LATE_POLICY` | 停机错过的提醒：`late_send` 补发并标注迟到 / `drop` 丢弃 | late_send |
| `REMINDER_LATE_WINDOW_HOURS` | 提醒最长补发窗口（小时） | 24 |
| `NUDGE_KILL_SWITCH` | 主动消息总开关（true = 只保留承诺类） | false |
| `MATERIALIZE_INTERVAL_SECONDS` | 排班员运行间隔（秒） | 300 |
| `ENABLE_CONSOLE` | 本地测试接口开关 | 0（关闭） |
| `LOG_LEVEL` | 日志详细程度 | INFO |

简报时间、免打扰时段、每日预算、消息类别开关不在这张表里——它们存在数据库的偏好表里，用对话就能改
（例如「把简报改到 9 点」「关闭简报」「免打扰改成 22 点到 8 点」），改完排班员会自动重排。

模型本身不用改代码：在方舟控制台「开通管理」里切换，`ark-code-latest` 这个别名会自动跟随（3-5 分钟生效）。

## 六、这份文档怎么用

1. **想改某个行为时**：先在这里找到对应部件，再对 AI 说「改第 X 节里的某个部件」，比说「改代码」精确得多
2. **怀疑 AI 说错时**：用它对照——比如 AI 说「已经实现了记忆功能」，你查第二节就知道没有
3. **了解进度时**：看第二节的三栏清单

**维护约定**：每个开发阶段结束时，我会同步更新这份文档的第二节（能力清单），并在第四节补充新的差距。技术细节永远只在 `contracts.md`，这里始终保持人话。每次修订后会把核对记录写进第七节。
