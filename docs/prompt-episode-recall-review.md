# 请评审：记忆抽取 episode 漏抽的修复方案

你是一名后端架构评审者。请判断下面的修复方案是否可以批准开工，指出遗漏风险，并回答末尾 3 个问题。

## 项目约束（不得违反）

- Butler：AI 原生时间管理后端，Python 3.12 + FastAPI + SQLAlchemy 异步 + PG16/pgvector。
- 状态与叙事分离：业务状态用强 schema 表，对话进 append-only event_log；向量、摘要、抽取事实都是可重建派生物，必须带 source_event_ids。
- LLM 只通过工具调用读写状态；确定性逻辑（时间换算、重复规则、校验）不交给 LLM。
- 记忆只 supersede 不原地更新；每条记忆有 provenance；推断类记忆不得驱动日程/计划/主动触达。
- 证据只认「用户消息」与「成功工具调用的结构化参数快照」；助手回复、外部内容不可作证据；quote 必须逐字回查。
- 契约见 docs/contracts.md，不得擅自改变字段含义。

## 实机验证结果

用户发了三句话：

1. 「记住我平时7:20起床。」→ 同步 remember 工具写入 slot/wake，值 07:20，stated 权重 0.8，嵌入与证据链均正确。
2. 「今天加班到了9:30。」→ Friday 即时回复正确（21:30），但**异步抽取没有产出任何记忆**。
3. 「提醒我明天交报告。」→ 正确创建 work_item「交报告」+ reminder trigger（11/7 09:00），符合预期。

异步 run 结果：events=3, candidates=1, actions={NOOP:1}，reason=`duplicate_slot`。唯一候选是起床槽位，被正确识别为与同步写入重复而丢弃（该去重行为符合设计）。

## 根因

查 llm_call 记录，`memory_extract` 的原始 reasoning 明确写道：

> "Event 2 '今天加班到了9:30' is an episode/state signal, but one-off, not long-term. … Don't output."

问题在系统提示词（app/memory/extract.py 的 SYSTEM_PROMPT）：

- 规则 3：只说「闲聊、一次性指令（如「提醒我交报告」）不算记忆」，没有区分「一次性指令」与「用户对自身状态的一次性陈述」。
- 全文没有任何一条告诉模型：带明确日期（今天/明天/后天/下周X/月底）的事件应抽为 `type=episode`、`scope.kind=on`、`date_text` 原样保留。

而评测基准 tests/evals/memory_cases.yaml 明确期望这些必须抽为 episode：

- e01「今天加班到九点」→ episode, scope on
- e02「今天睡到9点才起」
- e03「今天中午没吃饭」
- e04「今天提前下班了」
- e05「今天没去通勤，居家办公」
- e06「今天下午精力很差」
- r01–r08 相对日期类（明天下午三点开会 / 下周三出差 / 月底交房租 / 今天要加班 …）

影响：102 条评测用例中有 14 条 expect episode，按当前提示词会全部 miss。此前的 5 条冒烟评测只覆盖 slot，所以没暴露。

## 拟定修复方案 A（推荐）

1. 重写规则 3 的语义：一次性**指令**（建任务、设提醒、查询）不作为记忆；但用户对自身状态或事实的一次性陈述（尤其偏离常规的当日事件，如加班、睡过头、没吃饭、提前下班、居家办公、精力差）必须抽为 `episode`。
2. 新增规则：事件带明确参照日期（今天/明天/后天/本周X/下周X/月底）→ `type=episode`，`scope.kind=on`，`scope.date_text` 原样保留（不自行换算日期，换算由确定性代码完成）。
3. 明确 episode 不参与 slot 冲突判定，且不能覆盖 slot 的常规值（例外语义：今天加班不代表每天加班）。
4. `EXTRACTOR_VERSION` 由 `memory-extract-v1` 升为 `memory-extract-v2`（用于区分新旧抽取结果，不影响已有 run 的唯一约束）。
5. 回归测试：
   - 新增 3 条集成测试：带日期事件→episode；任务型指令→不抽；episode 不覆盖 slot；
   - 跑 e01/e02/r04 子集评测验证 recall；
   - 之后跑全量 102 条。

## 方案 B / C（备选）

- 方案 B：只补规则第 2 条，不改规则 3 语义，风险是模型仍可能把「加班」当一次性噪音丢弃。
- 方案 C：维持现状，把评测基准中的 episode 期望全部删掉。代价是放弃当日偏离事件的记录能力，后续简报/画像无法引用「昨天加班到九点」。

## 明确不做

不改数据库 schema；不改工具签名；不改权重公式；不动仲裁器/gate；不重跑历史事件。
